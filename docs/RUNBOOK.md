known defect in vibe-runbook, not a fact about this app.

## Is it up — **(filled by hand)**

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://star-cdhog5ebsq-uc.a.run.app/
```

`200` is alive. Three further checks, in the order worth running them:

```bash
# Google account linking survived the last deploy — a populated clientId.
curl -s https://star-cdhog5ebsq-uc.a.run.app/config.js | grep -c 'clientId": "[0-9]'

# The agent door challenges a stranger rather than answering one.
curl -s -o /dev/null -w "%{http_code}\n" -X POST \
  -H 'Content-Type: application/json' -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}' \
  https://star-cdhog5ebsq-uc.a.run.app/mcp        # expect 401

# No /api route answers a stranger with its schema.
curl -s -o /dev/null -w "%{http_code}\n" -X POST \
  -H 'Content-Type: application/json' -d '[1,2,3]' \
  https://star-cdhog5ebsq-uc.a.run.app/api/rooms  # expect 401, never 422
```

**The linking check is not optional.** `--set-env-vars` replaces the whole
variable set, so a deploy that loses `GOOGLE_OAUTH_CLIENT_ID` silently strips
account linking and the only symptom is a card that stops being offered.

## Deploy

```bash
bash scripts/deploy.sh
```

**(filled by hand)** It reads `FIREBASE_API_KEY` and `GOOGLE_OAUTH_CLIENT_ID`
out of `.env` when they are not already exported, so nothing has to be typed and
no secret goes on a command line. Builds from source via Cloud Build; **takes 8
to 12 minutes** and the build timeout is set to 1500s because the 10-minute
default expired mid-build on 2026-08-13 and returned `EXPIRED:` with nothing
after the colon.

`--max-instances=1` and `--min-instances=1` are both load-bearing rather than
tuning — see `docs/INFRASTRUCTURE.md`. Neither alone is enough.

## Roll back — **(filled by hand)**

Cloud Run keeps every revision, so a rollback is a traffic move rather than a
rebuild.

```bash
gcloud run revisions list --service star --region us-central1 \
  --project star-research-dept --format="value(metadata.name)"

gcloud run services update-traffic star --region us-central1 \
  --project star-research-dept --to-revisions=<REVISION>=100
```

**Confirming it took effect** — this is the part the tool asked about, and it is
the same two-step used to confirm every deploy this week:

```bash
# 1. the service agrees about which revision is serving
gcloud run services describe star --region us-central1 \
  --project star-research-dept --format="value(status.latestReadyRevisionName)"

# 2. a served asset carries a string only that revision has
curl -s https://star-cdhog5ebsq-uc.a.run.app/scriptcheck.js | grep -c '<some marker>'
```

Step 2 is the one that matters. A revision name is what Cloud Run *says*;
the served file is what a reader actually gets, and those have disagreed here
before — a deploy reported success while the browser held the previous build.

> **Not yet exercised.** The `update-traffic` command above has never been run
> on this service. The revision list and both confirmation steps have been, many
> times. Treat the rollback itself as untested until it isn't.

## Logs and observability — **(filled by hand)**

```bash
gcloud run services logs read star --region us-central1 \
  --project star-research-dept --limit 50
```

That is the whole of it: **there is no dashboard, no log sink and no metrics
stack.** Cloud Run's own request log is the only observability this service has,
and it is enough to have settled a real incident — the OAuth connector failure
of 2026-08-13 was diagnosed from it, where a 303 went straight back to the
callback with `error=invalid_scope` and no consent screen in between.

Application logs use `logger.exception` on the paths that can fail without
failing the request — saving a sweep, filing annotations, listing sweeps during
a refusal — so a swallowed failure is in this log and nowhere else.
